# フェーズ1〜3で発生した課題

作成日: 2026-05-28
対象: `security_monitor`（フェーズ1〜3、映像中継 = go2rtc v1.9.14）

## 本文書の位置付け

フェーズ1〜3（リポジトリ `security_monitor`、映像中継ソフトウェア go2rtc）で顕在化した課題と、その調査・対処の経緯を覚書として残します。
これらの課題が複合的に未解消であったことが、フェーズ4（`security_monitor_2`、MediaMTX + coturn）への全面再設計に至った理由であり、開発期間が長期化した直接の原因でもあります。

各課題の時系列・再設計後の解決策の概要は、[設計変遷履歴.md](設計変遷履歴.md) も参照してください。

---

## 1. WHEPサポートの制約

### 事象

go2rtc v1.9.14 のWebRTC配信は、独自エンドポイント `POST http://<rpi4-1>:1984/api/webrtc?src={name}` で **SDP Offer/Answer** を交換する設計となっており、**IETF draft-ietf-wish-whep に準拠した標準WHEPクライアント** から直接接続できませんでした。

> SDP Offer/Answer の交換手順、および標準WHEPクライアントの定義については [用語集.md](../用語集.md) の「**WHEP（WebRTC-HTTP Egress Protocol）**」「**SDP Offer/Answer**」を参照してください。

| 項目 | go2rtc v1.9.14 | 標準WHEP |
|---|---|---|
| エンドポイント | `/api/webrtc?src=<name>` | リソース単位のURI（例 `/whep/<stream>`） |
| HTTPメソッド | POST | POST |
| 応答 | SDP Answer のみ | SDP Answer + `Location` ヘッダ（ICEリスタート・DELETE用） |
| ICEリスタート | 未対応 | `PATCH <Location>` |
| セッション切断 | 未対応 | `DELETE <Location>` |

### 影響

- ブラウザ側JavaScriptに go2rtc 専用のSDP交換ロジックを書く必要があり、汎用WHEPクライアントライブラリを流用できませんでした。
- ICEリスタートやセッション明示終了の手段がなく、接続が劣化した際の回復をクライアント側で工夫する必要がありました（後述の「ICEギャザリングタイムアウト」「自動再接続」の独自実装に繋がっています）。

### 試行と結果

WHEP相当の動作を独自実装で代替し、フェーズ1〜2はそのまま運用しましたが、後述2・3の課題と合わせて根本対応は困難と判断しました。フェーズ4で MediaMTX v1.18.1（WHEP標準準拠）への置き換えにより解消しています。

## 2. LAN内ICE候補の解決困難

### 事象

LAN内のみの利用にもかかわらず、Chromeブラウザから rpi4-1（192.168.0.60）への WebRTC接続でICEネゴシエーションが完了せず、「接続中…」のまま映像が表示されない事象が頻発しました。

直接の原因は **ChromeのmDNS obfuscation**（プライバシー機能）です。Chromeは ICE candidate にLAN内のIPアドレスをそのまま乗せず、`<UUID>.local` 形式のmDNS名に置き換えて公開します。

```
candidate:1 1 UDP 2122252543 a1b2c3d4-....local 50000 typ host
```

go2rtc 側はこの `*.local` を名前解決できず、UDPホールパンチングが不成立となります。結果として、LAN内同士であってもICE接続が確立しない状況になっていました。

### 試行と結果

#### 試行A: `go2rtc.yaml` の `webrtc.candidates` に LAN IP を静的指定

```yaml
webrtc:
  candidates:
    - 192.168.0.60:8555  # rpi4-1 の IP アドレス（LAN 内アクセス用）
```

これは **サーバ側（go2rtc）** の候補をブラウザに通知するための設定で、サーバ側 candidate は正しくブラウザに届くようになりました。
しかし問題は **ブラウザ側（Chrome）が公開する candidate が `*.local` のまま** であることであり、上記設定では片側しか解決できず、ICE Connectivity Check は不安定なまま残りました。

#### 試行B: ICEギャザリングタイムアウトの追加（クライアント側）

旧設計ではICEギャザリング完了を無限に待ち続け、接続が固まる事象もありました。
ブラウザ側JavaScriptに3秒のタイムアウトを設けて緩和しています。

```javascript
// ICE ギャザリング完了待ち（最大3秒）
await new Promise((resolve) => {
    if (pc.iceGatheringState === 'complete') { resolve(); return; }
    pc.onicegatheringstatechange = () => {
        if (pc.iceGatheringState === 'complete') resolve();
    };
    setTimeout(resolve, 3000);
});
```

これは「無限ブロック」の回避には有効でしたが、ICEが成立しないこと自体は解決していません。

### 解決（フェーズ4）

rpi4-1 上に coturn を立てて STUN サーバとして使用する構成に変更しました（基本設計書「5.4 coturn STUNサーバーの役割と設定」）。
Chromeは STUN Binding Request により自身のLAN内IPを Server-Reflexive Candidate として取得し、その実IPを candidate として公開できるようになります。これにより `*.local` 問題を回避してLAN内ICEが安定して成立するようになりました。

```
# /etc/turnserver.conf（フェーズ4以降）
listening-port=3478
listening-ip=192.168.0.60
log-file=/var/log/coturn.log
```

## 3. go2rtc 起因の不具合

フェーズ1〜3を通じて、go2rtc v1.9.14 に起因する複数の事象が発生しました。代表的なものを以下に記録します。

### 3.1 H.264 FU-A 分割パケットのバグによる黒画面

#### 事象

カメラ映像が黒画面になる事象が頻発しました。go2rtc の H.264 FU-A（フラグメンテーションユニット A）の処理に起因するもので、フレーム再構築が失敗し、ブラウザ側がデコードを開始できない状態となります。

#### 試行と結果

フェーズ2では本問題の根本回避策として、配信プロトコルを **WebRTC → HLS（HTTP Live Streaming）** に切り替えました。

```javascript
// HLS.js リトライ強化設定（フェーズ2）
const hls = new Hls({
    fragLoadingMaxRetry:        30,   // デフォルト6 → 30（約90秒分）
    fragLoadingRetryDelay:    2000,
    fragLoadingMaxRetryTimeout: 8000
});
```

FU-Aバグは回避できましたが、HLSの構造的遅延（5〜15秒）でリアルタイム監視用途には不適と判明し、再設計が不可避となりました。

| 残存した問題 | 状況 |
|---|---|
| HLS の構造的遅延（5〜15秒） | HLS 仕様上リアルタイム性が低い |
| 黒画面誤検知 | `MANIFEST_PARSED` 前にポーリング開始で誤検知 |
| WiFi 不安定時の接続断 | AtomCam の WiFi 接続品質に依存 |
| 再接続仕様の複雑化 | 5秒待機・複数リトライ・状態管理が膨らんだ |

### 3.2 AtomCam 2 ビデオフリーズ未検知（go2rtc 自動再接続が機能しない）

#### 事象

ATOM Cam 2（cam2 = 玄関）のブラウザ表示が、ステータス「接続済み」のまま黒画面になる事象が **2026-04-21・2026-04-27** の2回発生しました。タイムスタンプが特定時刻で停止し、自動復旧しません。

```
4月27日 11:58:04 に cam2 のビデオが停止 → 約3時間放置されているところを発覚 → 15:04:10 まで未復旧
```

#### 調査結果（2026-04-27 レポートから要約）

- go2rtc REST API（`/api/streams`）の cam2 producer 受信バイト数を10秒間隔で計測したところ、ビデオ受信は完全停止し、オーディオのみ継続していました。

  | | T0 | T1（10秒後） | 変化 |
  |---|---|---|---|
  | video (id 1093) | 9,757,685,261 | 9,757,685,261 | **0（停止中）** |
  | audio (id 1095) | 1,479,626,880 | 1,479,795,840 | +168,960（正常） |

- カメラ本体（192.168.0.7）への新規RTSP接続では映像取得が可能でした（`ffmpeg` で当該時刻のフレームを取得確認）。問題は go2rtc とカメラ間の **既存RTSPセッション** に限定されています。
- go2rtc のログには cam2 に関する I/O timeout の記録がありませんでした。同日の cam1・cam3 では計15回発生しています。
- AtomCam 2 内 `netstat` 確認では、go2rtc との TCPセッション（`192.168.0.7:8554 → 192.168.0.60:52080`）は ESTABLISHED 状態を維持していました。

#### 根本原因

ATOM Cam 2 の v4l2rtspserver が、起動から約23時間26分後に **既存セッションへのビデオRTPパケット送信のみを停止** する事象（カメラのIngenic SoC H264ハードウェアエンコーダー or V4L2バッファ管理由来と推定）が直接原因です。

ただし、cam2 で **go2rtc 側の自動回復が機能しない構造的理由** は次の通りです。

| | ATOM Cam 2（cam2） | ATOM Cam Swing（cam1/cam3、当時の設定） |
|---|---|---|
| RTSPオーディオ | あり（L16 128kbps = 16KB/s） | なし |
| go2rtc I/Oタイムアウト | **発生しない** | 数時間ごとに発生 |
| ビデオフリーズ時の自動復旧 | **されない** | される（タイムアウト後に自動再接続） |
| 同事象の発生履歴 | 2026-04-21, 2026-04-27 | なし |

cam2 はオーディオストリームが **TCP コネクションのキープアライブとして機能** するため、ビデオが止まっても TCP は生存し続け、go2rtc 側で I/O timeout が起きません。結果として再接続トリガが発火しない、という構造になっていました。

#### 暫定対応（フェーズ3まで）

`go2rtc_watchdog.sh` を rpi4-1 上に systemd timer（5分間隔）で常駐させ、`/api/streams` の各カメラ `producers[0].receivers[video].bytes` が2回連続で増加しない場合に `systemctl restart go2rtc` を実行する仕組みを2026-04-27に投入しました。

| 項目 | 値 |
|---|---|
| 監視対象 | cam1・cam2・cam3（全台） |
| 監視間隔 | 5分（systemd timer） |
| 判定条件 | `bytes` が連続2回変化なし |
| アクション | `systemctl restart go2rtc` → 全状態リセット |
| 状態ファイル | `/var/lib/go2rtc-watchdog/{cam}.state` |

対象を全台にした理由は、2026-04-27 にカメラ音声設定ミスを修正して cam1・cam3 にもオーディオを有効化した結果、cam1/cam3 も cam2 と同じ「キープアライブで I/O timeout が起きない」状態となり、ウォッチドッグ非対象とできなくなったためです。

#### 副次的な事故（2026-04-21）

初回事象（2026-04-21）の調査中、`curl -X DELETE "http://localhost:1984/api/streams?src=cam2"` を実行した結果、**go2rtc.yaml から cam2 の定義が永久削除** されてしまいました。
go2rtc v1.9.14 の REST API は変更を設定ファイルに自動書き戻す仕様だったため、PUT 再追加も `streams: source not supported` で失敗し、最終的に `/etc/go2rtc/go2rtc.yaml` を手で復旧する事態となりました。
以降「`curl -X DELETE /api/streams` は運用中絶対に使用しない」を共通の禁止操作としています。

### 3.3 その他、go2rtc 周辺で対処した問題

フェーズ3への移行時（2026年5月初頭）に解消した代表的な事象です。

| 問題 | 原因 | 対処 |
|---|---|---|
| `sourceReconnectPause` で起動失敗 | MediaMTX v1.18.1 で当該パラメータが廃止 | 設定行を削除（MediaMTX 切替後） |
| ポート 8554 競合 | go2rtc が残存稼働 | `systemctl stop go2rtc` |
| `.local` 名前解決失敗 | Go ランタイムが mDNS 非対応 | RTSP ソースを IP アドレス指定に変更 |
| `codecs not supported by client` | AtomCam が LPCM 音声を配信し WebRTC が非対応コーデックと判定 | クライアント側で audio トランシーバーを削除 |
| ICE 接続失敗（接続中のまま固まる） | Chrome が IP を mDNS 名に変換（前述§2） | coturn で STUN サーバ構築 |
| ICE ギャザリングが完了しない | タイムアウト処理なし | 3秒タイムアウトを追加 |
| vostro が旧 go2rtc 画面を表示 | URL が localhost 参照 | URL を `http://rpi4-1.tsystem.gr.jp/` に変更 |
| 映像がセルからはみ出す | flex/grid の `min-height: auto` 問題 | `.camera-panel` に `min-height: 0` を設定 |

## 4. 残存していたリスクと、フェーズ4で得た改善

| 課題 | フェーズ1〜3 の状態 | フェーズ4 での状態 |
|---|---|---|
| WHEP標準対応 | 独自API、汎用クライアント不可 | MediaMTX が標準WHEPを提供 |
| LAN内ICE成立 | mDNS obfuscationで不安定 | coturn STUN で安定 |
| AtomCam2 ビデオフリーズ自動復旧 | 外部 watchdog で再起動依存 | MediaMTX の RTSP セッション管理に委譲（watchdog 廃止） |
| 配信プロトコル | go2rtc独自 / HLS 退避 → 遅延大 | WebRTC(WHEP) 直結、遅延 0.1〜0.5秒 |
| クライアント実装 | go2rtc専用ロジック | 標準WHEPに沿ったシンプル実装 |

これらをまとめて解決するには映像中継ソフトウェアの差し替えが最短経路と判断し、`security_monitor_2` リポジトリでの再設計に踏み切りました。
