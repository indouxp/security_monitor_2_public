## DEF-001: スワップのメトリクス取得・グラフ追加

**登録日**: 2026-05-19  
**状態**: 見送り中  
**関連コンポーネント**:

- `inventory/rpi4-1/collect_metrics.sh`
- `inventory/client/lin/push_metrics.sh`
- `inventory/client/win/push_metrics.ps1`
- `inventory/rpi4-1/push_daemon.py`
- `inventory/rpi4-1/@var@www@html@app.js`
- `inventory/rpi4-1/@var@www@html@index.html`
- `inventory/rpi4-1/@var@www@html@style.css`

### 内容

スワップ（仮想メモリ）の使用状況をメトリクスとして収集し、リソースモニター（Panel 4）に  
5つ目のグラフとして追加します。

### 見送り理由

現リリースはメモリ使用率（`mem`）でメモリ監視を行っており、スワップは対象外。  
スワップ使用の増加は OOM（メモリ枯渇）の予兆として有効な指標ですが、追加には以下の  
広範囲な変更が必要なため、現リリースのスコープ外としました。

- メトリクス収集スクリプト3種（Linux 2種・Windows 1種）への収集処理追加
- 送信 JSON への `swap` フィールド追加
- `push_daemon.py` の受信フィールド検証への影響確認
- `app.js` への5つ目のグラフ追加と Panel 4 レイアウト（4分割→5分割）変更
- `index.html` / `style.css` のレイアウト調整

### 想定対応

| 対象 | 想定内容 |
|---|---|
| `collect_metrics.sh` / `push_metrics.sh`（Linux） | `/proc/meminfo` の `SwapTotal`・`SwapFree` から `(SwapTotal - SwapFree) / SwapTotal × 100` を算出（`mem` と同方式）。`SwapTotal = 0` の環境は 0% とする |
| `push_metrics.ps1`（Windows） | ページファイル使用量から使用率を算出 |
| 送信 JSON | `swap` フィールド（使用率 %）を追加 |
| `push_daemon.py` | 受信フィールド検証（必須フィールド）への `swap` 追加要否を確認 |
| `app.js` / `index.html` / `style.css` | Panel 4 に `chart-swap` を追加。グラフ数 4→5 に伴うレイアウト変更。Y軸は 0–100 固定 |

### 補足

- `mem` が `MemAvailable` 基準（キャッシュ除外）の実使用率であるのに対し、`swap` を併用すると  
  「メモリが逼迫してスワップへの退避が始まった」状態を明確に捉えられます。
- スワップ未設定（`SwapTotal = 0`）のホストでは常に 0% となります。

## DEF-002: WireGuard 経由のリモート監視（外出先からのアクセス）

**登録日**: 2026-05-22  
**状態**: 見送り中  
**関連コンポーネント**:
- WireGuard サーバー（rpi4-1 もしくは常時稼働ノード／ルーター）※新規
- ルーター（ポートフォワード・DDNS 設定）
- クライアント端末（スマートフォン・PC の WireGuard クライアント）

### 内容

外出先から WireGuard VPN 経由で自宅 LAN に接続し、セキュリティモニターの WebUI  
（カメラ映像・リソースグラフ）を閲覧できるようにします。現在は LAN 内からのみアクセス可能です。

### 見送り理由

現リリースは基本設計書「1.2 設計方針」の **LAN内完結**（映像・メトリクスデータを外部に  
送信しない）に基づき、外部からのアクセスを対象外としています。リモート監視には VPN  
インフラの新規構築と外部公開に伴うセキュリティ検討が必要なため、現リリースのスコープ外としました。

### 想定対応

| 対象 | 想定内容 |
|---|---|
| WireGuard サーバー | rpi4-1 もしくは常時稼働ノード／ルーターに WireGuard を構築し、UDP ポート（既定 51820）を待ち受け |
| ルーター | WireGuard ポートのフォワード設定。固定グローバル IP でない場合は DDNS を利用 |
| クライアント端末 | スマートフォン・PC に WireGuard クライアントを導入し、鍵ペアと peer 設定を配布 |
| WebRTC 接続確認 | VPN 経由で WHEP・coturn STUN による WebRTC 映像が確立するか検証（ICE 候補の解決可否） |
| セキュリティ | 鍵管理、公開 UDP ポートの最小化、許可 peer の限定 |

### 補足

- WireGuard トンネル経由で自宅 LAN のサブネットへ到達するため、WebUI へは LAN 内と  
  同じ URL でアクセスできる見込み。
- WebRTC は VPN 経由だと ICE 候補の解決が LAN 内と異なる可能性があり、coturn の  
  設定見直しが必要になり得ます。
- 外部公開を伴うため、現行の「LAN内完結」方針からの転換となります。導入時は設計方針の改訂が前提です。

## DEF-003: AtomCamへのpingが通らない場合の対応

**登録日**: 2026-05-27  
**状態**: 見送り中  
**関連コンポーネント**: なし

### 内容

AtomCam からのストリーミングが途絶え、Atom V2 アプリからもデバイスが確認できなくなる事象が発生することがあります。処置優先としたため、原因は不明です。ping が通らない状態では、atomcam_tools 経由の SSH によるリブートも不可能であり、ソフトウェア的な復旧手段がありません。過去二度の発生時は、AtomCam の電源 OFF/ON およびホームルーターのリブートにより復旧しました。

### 見送り理由

過去二度の発生はいずれもホームルーターの WiFi に接続している AtomCam で発生しており、ホームルーター側の不具合の可能性があります。ルーターのリブートを恒久対応とすべきか判断するには原因調査が必要であり、発生頻度も二度と少ないため、調査を優先とします。また、恒久対応としてホームルーターの変更や WiFi アクセスポイントの追加など、機器購入が発生する可能性もあるため、現リリースのスコープ外としました。 


### 想定対応

| 対象      | 想定内容                                                     |
| --------- | ------------------------------------------------------------ |
| 原因調査  | AtomCam がネットワークから見えなくなる原因の特定（ホームルーター側の不具合か、AtomCam 側の問題か） |
| rpi4-1    | 一定間隔で各 AtomCam への ping を行い、疎通が途絶えた時点でルーターを再起動する。 |
| rpi4-0    | 〃                                                           |
| rpi3(dns) | 〃                                                           |

### 補足

- 自動復旧を実装する場合、rpi4-0、rpi4-1、rpi3 の 3 台が独立にルーター再起動をトリガーすると競合するため、マスター選出や結果集約など、3 台間の同期の仕組みが必要となります。
- 原因調査の結果によっては、ルーターリブートではなく、機器変更（ホームルーターの変更、WiFi アクセスポイントの追加等）による根本対応となる可能性があります。

## DEF-004: Windows クライアントの CPU 温度の正確な取得（LibreHardwareMonitorLib 導入）

**登録日**: 2026-05-28
**状態**: 見送り中
**関連コンポーネント**:

- `inventory/client/win/push_metrics.ps1`
- `inventory/client/win/register_task.ps1`
- Windows クライアント側の追加配置物（`LibreHardwareMonitorLib.dll`）

### 内容

Windows クライアントの CPU 温度メトリクス（`temp`）が、CPU 実温度ではなく常に約 30℃（実測 29.8℃）固定の値となっています。原因は現実装が WMI クラス `MSAcpi_ThermalZoneTemperature` に依存しており、これがマザーボード/シャーシ周辺の鈍い温度しか返さないためです。CPU パッケージ温度は MSR（Model Specific Register）にあり、Windows 標準 WMI からは取得できません。

DELL Precision 3620 での実測値：

| InstanceName | CurrentTemperature (1/10 K) | TempC |
| --- | --- | --- |
| `ACPI\ThermalZone\TZ00_0` | 3010 | 27.8 |
| `ACPI\ThermalZone\TZ01_0` | 3030 | 29.8 |

現行コード（`push_metrics.ps1` の `Get-CpuTempC`）は両ゾーンの最大値を採用するため、ほぼ 29.8℃ で張り付きます。値はわずかに変動するものの CPU 負荷とは相関せず、温度監視としての意味を成していません。

### 見送り理由

正確な CPU 温度の取得には外部ライブラリ（`LibreHardwareMonitorLib.dll`）の導入が必要であり、以下の付帯対応が発生します。フェーズ4 のスコープに対して影響範囲が広く、追加検証も要するため、現リリースのスコープ外としました。

- Windows クライアントへの DLL 配布・配置の運用設計（バージョン管理・更新手順含む）
- `LibreHardwareMonitorLib` 初回利用時に `WinRing0` カーネルドライバのロードが発生し、**管理者権限**が必須となる
- タスクスケジューラの実行アカウントを「ユーザー」から「SYSTEM もしくは管理者ユーザー + 最上位の特権で実行」に変更する必要があり、`register_task.ps1` の修正と再登録運用が伴う
- ライセンス（MPL 2.0）に基づく利用条件の確認
- 既存の `Get-CpuTempC` 単体テスト（フォールバック動作の検証）の再構築

### 想定対応

| 対象 | 想定内容 |
| --- | --- |
| `LibreHardwareMonitorLib.dll` 配置 | GitHub の LibreHardwareMonitor リリースから取得し、Windows クライアントの `C:\opt\LibreHardwareMonitor\LibreHardwareMonitorLib.dll` に配置。バージョン固定 |
| `push_metrics.ps1` (`Get-CpuTempC`) | `Add-Type -Path` で DLL をロードし、`LibreHardwareMonitor.Hardware.Computer` で `IsCpuEnabled = $true` として CPU センサーを列挙、`SensorType.Temperature` のうち最大値（または Package 温度）を採用。失敗時は従来どおり 0.0 にフォールバック |
| `push_metrics.ps1` (フォールバック) | DLL が見つからない／ドライバロード失敗時は現行の `MSAcpi_ThermalZoneTemperature` を二次手段として残し、ログに切替理由を記録 |
| `register_task.ps1` | タスクの実行アカウントを管理者権限に変更し、「最上位の特権で実行」フラグを設定。再登録手順を README に追記 |
| 検証 | CPU に対し `stress`／高負荷処理を流し、`temp` が負荷に応じて上昇することを Windows クライアントのローカル履歴（`%APPDATA%\push_metrics\history.ndjson`）および rpi4-1 側 `/api/my-history` の双方で確認 |
| ドキュメント | README に DLL 入手元・配置パス・必要権限・既知問題（WinRing0 のドライバ署名警告等）を追記 |

### 想定実装（参考コード）

```powershell
function Get-CpuTempC {
    $dllPath = 'C:\opt\LibreHardwareMonitor\LibreHardwareMonitorLib.dll'
    try {
        if (-not (Test-Path $dllPath)) { throw "DLL not found: $dllPath" }
        Add-Type -Path $dllPath
        $computer = New-Object LibreHardwareMonitor.Hardware.Computer
        $computer.IsCpuEnabled = $true
        $computer.Open()
        $maxT = 0.0
        foreach ($hw in $computer.Hardware) {
            $hw.Update()
            foreach ($s in $hw.Sensors) {
                if ($s.SensorType -eq [LibreHardwareMonitor.Hardware.SensorType]::Temperature `
                    -and $null -ne $s.Value -and $s.Value -gt $maxT) {
                    $maxT = [double]$s.Value
                }
            }
        }
        $computer.Close()
        if ($maxT -le 0) { throw "no temperature sensor found" }
        [math]::Round($maxT, 1)
    } catch {
        Write-Log "WARN LibreHardwareMonitor temp unavailable, fallback to ACPI: $_"
        # 二次フォールバック: 従来の ACPI 経由（実機では固定値となる既知問題あり）
        try {
            $zones = Get-WmiObject MSAcpi_ThermalZoneTemperature `
                -Namespace 'root/wmi' -ErrorAction Stop
            if ($null -eq $zones) { return 0.0 }
            $maxK10 = ($zones | Measure-Object CurrentTemperature -Maximum).Maximum
            [math]::Round(($maxK10 - 2732) / 10.0, 1)
        } catch {
            Write-Log "WARN CPU temp unavailable: $_"
            0.0
        }
    }
}
```

### 補足

- 本問題は DELL Precision 3620 の BIOS 仕様（ACPI サーマルゾーンに CPU 実温度を公開しない）に起因するもので、Windows 側コードのバグではありません。同様の挙動は多くの Intel デスクトップ／ノートで一般的に発生します。
- 代替案として、温度取得を諦め `N/A` 表示・グラフ非表示とする案（軽量）もありますが、Linux クライアント／rpi4-1 では正確に取得できているため、表示の一貫性の観点から本案（LibreHardwareMonitorLib 導入）を第一候補とします。
- LibreHardwareMonitorLib は `WinRing0` ドライバを使用するため、Windows のドライバ署名ポリシーやセキュリティソフトとの干渉に関する事前確認が必要です。
