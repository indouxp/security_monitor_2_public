## BUG-001: Windows タスクスケジューラが登録直後に起動しない

**発見日**: 2026-05-11  
**状態**: 修正済み  
**影響コンポーネント**: `inventory/client/win/register_task.ps1`

### 現象

`register_task.ps1` を実行してタスクを登録しても、メトリクスが rpi4-1 に届きません。  
タスクスケジューラ GUI でタスクを確認すると `Ready` 状態のまま実行されていません。

### 原因

`AtLogOn` トリガーは **次回ログイン時** に初めて発火します。  
タスク登録時点でユーザーがすでにログイン済みの場合、再ログインするまでトリガーが発火しません。

### 修正

デュアルトリガー方式を採用:

1. **Once トリガー**: 登録の15秒後に発火し、以降1分ごとに繰り返します
2. **AtLogOn トリガー**: 次回ログオン時に発火し、以降1分ごとに繰り返します

両トリガーに同一の `RepetitionPattern` を割り当てることで間隔が統一されます。  
`MultipleInstances=IgnoreNew` で両トリガーが重なっても多重起動しません。

```powershell
$triggerOnce = New-ScheduledTaskTrigger `
    -Once `
    -At (Get-Date).AddSeconds(15) `
    -RepetitionInterval (New-TimeSpan -Minutes $INTERVAL_MIN)

$repPat = $triggerOnce.Repetition
$triggerLogon = New-ScheduledTaskTrigger -AtLogOn
$triggerLogon.Repetition = $repPat

Register-ScheduledTask ... -Trigger @($triggerOnce, $triggerLogon) ...
```

## BUG-002: Windows タスク実行時に画面がフラッシュする

**発見日**: 2026-05-11  
**状態**: 修正済み  
**影響コンポーネント**: `inventory/client/win/register_task.ps1`、`inventory/client/win/run_hidden.vbs`（新規）

### 現象

タスクスケジューラが `push_metrics.ps1` を実行するたびに、画面が一瞬フラッシュ（白く点滅）します。

### 原因

`powershell.exe -WindowStyle Hidden` を指定しても、タスクスケジューラ経由では  
PowerShell の起動時に一瞬ウィンドウが生成・破棄されます（GDI描画の副作用）。

### 修正

`wscript.exe` + `run_hidden.vbs` 経由で PowerShell を起動する方式に変更しました。  
`WScript.Shell.Run(command, 0, True)` の第2引数 `0`（window style = hidden）で  
完全に不可視のプロセスとして PowerShell を起動できます。

```vbs
Dim WshShell, script
script = CreateObject("Scripting.FileSystemObject").GetParentFolderName( _
    WScript.ScriptFullName) & "\push_metrics.ps1"
Set WshShell = CreateObject("WScript.Shell")
WshShell.Run "powershell.exe -NonInteractive -ExecutionPolicy Bypass -File """ _
    & script & """", 0, True
Set WshShell = Nothing
```

`register_task.ps1` のアクションを `wscript.exe` に変更:

```powershell
$VBS_PATH = "$PSScriptRoot\run_hidden.vbs"
$action = New-ScheduledTaskAction `
    -Execute 'wscript.exe' `
    -Argument "`"$VBS_PATH`""
```

## BUG-003: Windows クライアントの DNS 名前解決失敗（WSL2 環境）

**発見日**: 2026-05-11  
**状態**: 修正済み（設定手順追加）  
**影響コンポーネント**: `docs/環境設定手順書.md` Section 6.3

### 現象

`push_metrics.ps1` が `http://rpi4-1.tsystem.gr.jp/api/push` へのPOSTに失敗します。  
`ping rpi4-1.tsystem.gr.jp` が `NXDOMAIN` を返します。

### 原因

WSL2 インストール済みの Windows では Hyper-V 仮想スイッチが DNS クエリに干渉します。  
仮想スイッチの DNS リゾルバーが LAN 上のプライベートドメイン（`*.tsystem.gr.jp`）に対して  
NXDOMAIN を返し、かつ LAN DNS（`192.168.0.254`）より先に応答するため名前解決が失敗します。

### 修正

NRPT（名前解決ポリシーテーブル）を設定し、対象ドメインのクエリを LAN DNS に強制します。

```powershell
# 管理者として実行（一度のみ）
Add-DnsClientNrptRule -Namespace ".tsystem.gr.jp" -NameServers "192.168.0.254"
ipconfig /flushdns
```

この設定はシステム再起動後も維持されます。

## BUG-004: グラフのX軸目盛線が表示されない

**発見日**: 2026-05-11  
**状態**: 修正済み  
**影響コンポーネント**: `inventory/rpi4-1/@var@www@html@app.js`

### 現象

リソースグラフのX軸に `HH:MM` ラベルが1件しか表示されない、または全く表示されません。  
グラフのグリッド線も消えています。

### 原因（2件）

**原因A: `maxTicksLimit` によるダウンサンプリング**

Chart.js v4 の linear スケールで `stepSize:300` を設定すると、エポック（Unix秒 = 0）を起点に  
tick が生成されます。現在時刻（例: 1747000000秒）では tick 数が約583万個になり、  
`maxTicksLimit:13` のダウンサンプリングで5分刻みの tick がすべて省略されます。

**原因B: `callback` で `null` 返却するとグリッド線も消える**

`callback(value)` で tick に label が不要な場合に `null` を返すと、  
Chart.js v4 ではラベルだけでなくグリッド線まで非表示になります。

### 修正

- `stepSize` と `maxTicksLimit` を廃止
- `afterBuildTicks` で `Math.ceil(axis.min / 300) * 300` を起点に300秒刻みの tick を手動生成
- `callback` は常に `HH:MM` 文字列を返します（null を返しません）
- `grid: { color: '#333' }` でグリッド線を明示設定

```javascript
afterBuildTicks(axis) {
    if (!axis.min || axis.min < 1000000000) return;
    const start = Math.ceil(axis.min / 300) * 300;
    const ticks = [];
    for (let sec = start; sec <= axis.max; sec += 300) {
        ticks.push({ value: sec });
    }
    axis.ticks = ticks;
},
```

## BUG-005: グラフの左端にデータが表示されない（左端ギャップ）

**発見日**: 2026-05-11  
**状態**: 修正済み  
**影響コンポーネント**: `inventory/rpi4-1/@var@www@html@app.js`

### 現象

グラフのX軸左端（最古のデータ付近）に常に空白が生じます。  
左端の時刻目盛にデータ点がプロットされていません。

### 原因

X軸の最小値 `minSec` は5分アライメント済み（`Math.floor(startSec / 300) * 300`）のため、  
`startSec`（実際のデータ開始時刻）より最大5分前になります。  
一方、`toXY` フィルターが `x >= startSec - 5` で始まっていたため、  
`minSec` ～ `startSec` の範囲（最大5分）にデータ点が存在せず左端ギャップが発生します。

### 修正

`toXY` フィルターの下限を `minSec - 65` に変更し、左端目盛より前のアンカー点を含めます。  
Canvas の clip 機能により左端より前の点は描画されませんが、最初の点への線分が  
左端から引かれることでギャップが解消されます。

あわせて `n`（取得行数バッファ）を `+5` から `+15` に拡大し、  
5分アライメントオフセット分のデータを確実に含めます。

```javascript
const n = Math.ceil(durationSec / COLLECT_INTERVAL) + 15;
const toXY = (data, valFn) => data
    .map(d => ({ x: tsToUnix(d.ts), y: valFn(d) }))
    .filter(p => p.x >= minSec - 65 && p.x <= endSec + 5);
```

## BUG-006: Windows クライアントに mem_total フィールドがない

**発見日**: 2026-05-11  
**状態**: 修正済み  
**影響コンポーネント**: `inventory/client/win/push_metrics.ps1`

### 現象

Windowsクライアントのメトリクスグラフで、凡例にメモリ総量（GB）が表示されません（`NaN GB` 等）。  
`push_metrics.ps1` が送信するJSONに `mem_total` フィールドが含まれていませんでした。

### 原因

Linux の `push_metrics.sh` は `mem_total`（KB 単位の総メモリ量）を送信しますが、  
Windows 版の `Get-MemPercent()` は使用率(%)のみを返しており、`mem_total` が未実装でした。

### 修正

`Get-MemPercent()` を `Get-MemInfo()` にリネームし、ハッシュテーブルで返すよう変更しました。

```powershell
function Get-MemInfo {
    $totalBytes = (Get-WmiObject Win32_ComputerSystem).TotalPhysicalMemory
    $totalMB    = [math]::Round($totalBytes / 1MB, 0)
    $availMB    = (Get-Counter '\Memory\Available MBytes' -SampleInterval 1).CounterSamples.CookedValue
    if ($totalMB -le 0) { return @{ pct = 0.0; total_kb = 0 } }
    @{
        pct      = [math]::Round(($totalMB - $availMB) / $totalMB * 100, 1)
        total_kb = [long]($totalBytes / 1024)
    }
}
```

ペイロードに `mem_total` を追加:

```powershell
$payload = [ordered]@{
    ...
    mem       = $memInfo.pct
    mem_total = $memInfo.total_kb   # KB 単位（Linux と同形式）
}
```

## BUG-007: 環境設定手順書の ExecutionPolicy 記載誤り

**発見日**: 2026-05-11  
**状態**: 修正済み  
**影響コンポーネント**: `docs/環境設定手順書.md` Section 6.2

### 現象

`register_task.ps1` 内では `-ExecutionPolicy Bypass` を指定していますが、  
手順書には `Set-ExecutionPolicy RemoteSigned` と記載されていました。

### 修正

`Set-ExecutionPolicy Bypass -Scope LocalMachine` に修正しました。  
`run_hidden.vbs` も `Bypass` で PowerShell を起動するため、ポリシーを一致させます。
