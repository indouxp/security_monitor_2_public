## 概要

本書は、トラブルシューティング時に確認すべきログ・データファイルの出力先を、ホスト別・コンポーネント別に整理した一覧です。

「ホスト」「コンポーネント」「ログ／データ出力先」「出力契機」「確認方法」「ローテーション設定の有無」を網羅しています。本リポジトリ内に設定ファイル／スクリプトが存在しない項目（Samba 等）は OS デフォルトを示し、実機確認が必要な旨を補足しています。

## 8. 主要なログメッセージの解説

### 8.1 MediaMTX のよく出る警告（WAR）

`/var/log/mediamtx.log` で頻繁に観察される代表的な警告です。いずれもサービス停止には至りませんが、映像品質に影響するため傾向監視が必要です。

#### `[path X] [RTSP source] N RTP packets lost`

| 項目 | 内容 |
|---|---|
| 意味 | RTSP ソース（AtomCam）から rpi4-1 への RTP パケットが N 個欠落した |
| 重要度 | WAR（警告）— サービス継続可、映像品質に影響 |
| 原因 | RTP は UDP ベースで再送がないため、ネットワーク品質の影響を直接受けます。無線 LAN の干渉・混雑（AtomCam Swing は無線）、スイッチ／AP 経路の輻輳、カメラ側エンコーダの処理遅延 |
| 影響 | 一瞬の映像途切れ・ブロックノイズ・I フレーム再取得までの画質低下 |
| 対処 | 一過性なら無視可。継続多発時は無線環境改善（チャネル変更・AP 増設・距離短縮）、可能なら有線化 |

#### `[path X] N processing errors, last was: invalid FU-A packet (non-starting)`

| 項目 | 内容 |
|---|---|
| 意味 | H.264 の RTP ペイロード形式（RFC 6184）における FU-A（Fragmentation Unit type A）の処理エラー。1 つの NAL ユニットを複数 RTP パケットに分割する仕組みで、`non-starting` は最初の断片（S=1 ビット）を受信せずに後続断片を先に受信した状態 |
| 重要度 | WAR（警告）— サービス継続可 |
| 原因 | 上記 RTP パケットロスの **派生エラー**。先頭断片が欠落した時に必然的に発生します |
| 影響 | 該当 NAL ユニットを破棄するため、フレーム欠損 → I フレーム到達まで一時的な静止／崩れ |
| 対処 | 単独で対処するものではなく、上記 packet loss の対策に従います |

#### 緊急対応への昇格判断

WAR が ERR に昇格する事象（接続切断 `connection closed`・再接続失敗 `failed to reconnect`・パスのドロップ等）が出始めたら緊急対応へ移行します。WAR レベルの頻度増加は品質低下のシグナルとして記録を残します。

### 8.2 nginx access ログの典型パターン

`/var/log/nginx/access.log` で観察される正常時のアクセスパターン。combined log 形式（`IP - - [time] "request" status size "referer" "UA"`）。

#### 30 秒周期で繰り返される正常リクエスト

| リクエスト | 出元 | レスポンス | 意味 |
|---|---|---|---|
| `GET /api/my-history` | ブラウザ（vostro 等） | 200 OK（数百 KB） | クライアントメトリクス履歴の取得（グラフ描画用） |
| `GET /data/rpi4-1-history.ndjson` | ブラウザ | 200 OK（数百 KB） | rpi4-1 自身のメトリクス履歴の取得（同上） |
| `POST /api/push` | 各メトリクスクライアント（curl） | 200 OK（2 バイト程度） | クライアントが自ホストのメトリクスを 30 秒ごとに送信 |

これらが 30 秒間隔で繰り返されるのは設計通りの動作。

#### アクセス元 IP からのホスト識別

| IP | ホスト | 代表 UA |
|---|---|---|
| `192.168.0.154` | vostro（Chrome キオスク端末） | Chrome/* + curl/* |
| `192.168.0.206` | macmini2010 | curl/8.5.0 |
| その他 `192.168.0.x` | Windows クライアント等（README ノード一覧で確認） | curl/* または PowerShell の HTTP client |

#### 異常パターンの目安

| 観察事項 | 想定原因・対処 |
|---|---|
| `4xx`（特に 404） | URL タイポ、リソース未デプロイ、release 漏れ。`/api/*` 系は push_daemon と nginx プロキシ設定の整合を確認 |
| `5xx`（特に 502/504） | バックエンド（push_daemon.py）の停止／応答遅延。`journalctl -u push-daemon` を確認 |
| 30 秒周期が大きく崩れる | クライアント側 systemd timer／タスクスケジューラの停止、ネットワーク断 |
| ノード一覧に無い IP | 未登録機からの POST／GET。意図しない接続なら遮断要否を検討 |
| POST サイズが極端に大きい | 不正クライアント／攻撃の可能性（本系では数 KB 程度が想定） |

#### error ログ（`/var/log/nginx/error.log`）の確認

access ログに 4xx／5xx が出た場合は併せて error ログを参照します。upstream timeout、permission denied、SSL handshake 失敗等の原因が記録されます。

### 8.3 nginx error ログの典型パターン

`/var/log/nginx/error.log` のフォーマット:

```
TIME [LEVEL] PID#TID: *CONN_ID MESSAGE, client: IP, server: HOST, request: "METHOD URI", host: "HOST", referrer: "URL"
```

LEVEL は `debug` < `info` < `notice` < `warn` < `error` < `crit` < `alert` < `emerg` の順で重要度が上がります。本系で観察される代表メッセージを整理します。

#### `open() "..." failed (2: No such file or directory)` — ENOENT

| 項目 | 内容 |
|---|---|
| 意味 | nginx が要求された静的ファイルを開けなかった（`errno=2 ENOENT`）。HTTP 応答は 404 |
| 重要度 | error レベルですが、要求ファイルの種類により実害は変動します |
| 代表例 | `/favicon.ico` 未配置時 — ブラウザがタブアイコン取得用に自動アクセスして発生 |
| 影響 | favicon の場合: ブラウザのタブアイコンが出ないだけ。アプリ用ファイルなら release 漏れ等の重大事象 |
| 対処 | アプリ用ファイルなら release.sh で再配備。favicon なら `/var/www/html/favicon.ico` を配置するか、nginx site 設定で `location = /favicon.ico { access_log off; log_not_found off; }` を追加してログ抑止 |

#### その他、本系で監視すべき error メッセージ

| メッセージ例 | 想定原因 |
|---|---|
| `upstream timed out (110: Connection timed out) while reading response header from upstream` | push_daemon.py がハング／応答遅延。`journalctl -u push-daemon` を確認 |
| `connect() failed (111: Connection refused) while connecting to upstream` | push_daemon.py が停止中。`systemctl status push-daemon` を確認 |
| `permission denied` | 静的ファイル／ログディレクトリのパーミッション設定ミス |
| `SSL_do_handshake() failed` | HTTPS 化した場合に発生。証明書設定を確認（本系は LAN 内 HTTP のため通常発生しない） |
| `client intended to send too large body` | POST ボディが `client_max_body_size` を超過 |

#### 重要度判断の指針

- **error / warn** が散発: 多くは無害（favicon 等）。種類を確認し、無害なら抑止 or 放置
- **error が継続多発**: 真の障害の可能性大。access ログの 5xx と相関を取って原因特定
- **crit / alert / emerg**: 即時対応必要（OS リソース枯渇・設定不正等）

### 8.4 push-daemon journal の典型パターン

`journalctl -u push-daemon -f` で観察される push_daemon.py のログです。Python の `logging` モジュールが標準出力に書いたものを systemd が journal に取り込みます。

ログフォーマット:

```
MONTH DAY HH:MM:SS HOSTNAME python3[PID]: TIMESTAMP LEVEL MESSAGE
```

- 前半は journald のメタ情報（ホスト名・プロセス[PID]）
- 後半は push_daemon.py 由来（asctime は `%Y%m%d.%H%M%S` 形式、`LEVEL` は `INFO` / `WARNING` / `ERROR`）

#### `INFO saved <IP> cpu=X temp=Y disk_rw=Z mem=W` — 正常受信

| 項目 | 内容 |
|---|---|
| 意味 | クライアントから POST された JSON メトリクスを受領し、ローカル NDJSON に保存した |
| 発生 | クライアントからの `POST /api/push` 受信時（30 秒ごと） |
| 値の意味 | `cpu`=CPU 使用率 %、`temp`=CPU 温度 ℃、`disk_rw`=ディスク I/O バイト数、`mem`=メモリ使用率 % |
| 重要度 | INFO（正常動作の記録） |
| 想定頻度 | クライアント数 × 30 秒間隔（例: 3 台で 6 件/分） |

PID が長時間同一 = サービスが安定継続中。PID が頻繁に変わる場合は `Restart=always` の繰り返し再起動が疑われるため、ERR を含む直前ログを確認。

#### 想定される異常メッセージ

| ログ例 | 想定原因 | 対処 |
|---|---|---|
| `WARNING missing required fields: ...` | 必須フィールド（`hostname`/`cpu`/`temp`/`disk_rw`/`mem`）欠落 | 送信元クライアントの実装／環境を確認 |
| `ERROR invalid JSON: ...` | POST ボディが JSON 形式不正 | クライアントの送信内容を確認、nginx 経由なら content-type 等も確認 |
| `ERROR failed to write history: ...` | NDJSON ファイル書き込み失敗 | 出力先ディレクトリのパーミッション・ディスク残量を確認 |
| 出力が一定時間途絶 | クライアント停止 or サービス停止 | `systemctl status push-daemon`、クライアント側 systemd timer／タスクスケジューラを確認 |
| 出力が異常頻度 | 送信間隔の設定ミス or 攻撃 | クライアント側スクリプトを確認、未登録 IP からなら遮断検討 |

#### 値の妥当性チェック

ログ中の値から、明らかな異常を発見できます：

| 値 | 通常範囲 | 異常時の対処 |
|---|---|---|
| `cpu` | 0〜100 | 100 に張り付き続けるならクライアント側の負荷調査 |
| `temp` | 35〜70 ℃ | 75 ℃ 超で冷却・熱対策、Mac mini 2010 等の古いハードはやや高め |
| `disk_rw` | 0〜数十 MB | 異常に大きい値が継続するならディスク I/O 負荷の原因調査 |
| `mem` | 0〜100 | 90 超が続くならメモリリークやプロセス過剰を疑う |

### 8.5 collect-metrics journal の典型パターン

`journalctl -u collect-metrics -f` で観察される rpi4-1 自己メトリクス収集サービスのログ。
Type=oneshot サービスを 30 秒間隔の timer (`OnCalendar=*:*:00/30`) で起動する構成。

#### 正常時に観察される 3 種類のメッセージ（全て systemd 由来）

| メッセージ | 意味 |
|---|---|
| `Starting collect-metrics.service - ...` | timer が発火し、サービスを起動 |
| `collect-metrics.service: Deactivated successfully.` | スクリプトが exit 0 で正常終了 |
| `Finished collect-metrics.service - ...` | サービスの終了処理完了 |

#### 正常時の時系列パターン

```
19:42:00  Starting          ← 30 秒境界で発火
19:42:01  Deactivated       ← 約 1 秒で実行完了
19:42:01  Finished
19:42:30  Starting          ← きっかり 30 秒後
19:42:31  Deactivated
...
```

- 30 秒間隔（`OnCalendar=*:*:00/30` 設定通り）
- 各実行 ≈ 1 秒で完了（軽量処理）
- 全て `Deactivated successfully` で正常終了

#### スクリプト自体の出力がない理由

`collect_metrics.sh` は正常時に標準出力へ何も書かない設計です。エラー時のみ `${LOG_FILE}`（既定 `/home/indo/log/collect_metrics.log`）に追記します。`StandardOutput=journal` でも、出すものがないため journal にはサービス状態変化だけが残ります。

これは設計上意図的（30 秒×24 時間 = 2880 件/日が journal を占有するのを防ぐため）。**正常時に「ログがない」のが正しい状態**。

#### 想定される異常パターン

| ログ例 | 想定原因 | 対処 |
|---|---|---|
| `Failed with result 'exit-code'` | スクリプトが exit 1 終了。ERR トラップが発火 | 直前の stderr / ERR メッセージを確認、`${LOG_FILE}` 末尾も参照 |
| `ERROR rc=N line=M: <cmd>` | スクリプト内 ERR トラップ出力（StandardError=journal 経由） | エラー行と戻り値から原因特定 |
| 30 秒境界が大きくズレる | timer の `AccuracySec` 設定、システム負荷、時刻ずれ | `systemctl list-timers collect-metrics`、ntpd 状態を確認 |
| `Starting` が長時間出ない | timer 停止／無効化、systemd 状態異常 | `systemctl status collect-metrics.timer` で有効化状態を確認 |
| 各実行に数秒以上かかる | スクリプト内の外部コマンド遅延（`/proc` 読み取り等） | 異常な負荷状態を確認 |

#### 確認コマンドの典型例

```bash
# 過去 10 件の起動状況
journalctl -u collect-metrics -n 10

# エラーレベルのみ抽出
journalctl -u collect-metrics -p err

# timer の状態確認
systemctl list-timers collect-metrics.timer

# スクリプトのエラーログ（あれば）
tail -n 30 /home/indo/log/collect_metrics.log
```

## 9. 注意事項

- **ローテーション設定が未設定の項目**: MediaMTX、coturn、`collect_metrics.log`、rsync ログ。容量増大に注意。必要に応じて `/etc/logrotate.d/` に設定を追加してください。
- **journal の保持期間**: systemd journal はディストリビューションのデフォルト設定に依存します。長期保存が必要な場合は `/etc/systemd/journald.conf` の `SystemMaxUse=` 等を調整してください。
- **エラー時のみの記録**: クライアント側の `push_metrics.log` は ERR トラップ発火時のみ追記されます。通常時に記録がないのは正常です。
- **本リポジトリ外の設定**: nginx・Samba・cron スクリプト等、本リポジトリで管理していない設定については実機側で確認が必要です。
